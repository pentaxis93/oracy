# Oracy v0.2.0 Specification — Working Draft for Operator Review

*Status: Working draft. Not committed to `spec/`. Captures operator
intent stated through May 6 2026 plus structural gaps requiring
operator decision. Next session opens by reviewing, tuning, and
committing this to authoritative status before Codex decomposition
into epics/issues.*

*Predecessor: v0.1.0 production cutover, May 6 2026.*

---

## v0.2.0 Vision

**v0.2.0 = ready for actual users.**

v0.1.0 shipped Oracy to an N=1 operator on principled substrate.
v0.2.0 takes Oracy from "shipped to operator" to "shipped to people
who are not the operator." That chasm crosses multiple themes that
v0.1.0 deliberately deferred.

What "ready for actual users" means functionally:

- Distributable through public channels (no sideload)
- Authenticatable by people who don't share the operator's
  infrastructure
- Sustainable economically (paid; not free)
- Legally compliant for public distribution
- Observable by users (not just operator)
- Reliable at scale beyond N=1

### Confirmed scope

- **Release channels.** Internal testing track, closed/open beta,
  production track — which ones get used and how.

### Cross-cutting

- Touches **Repo architecture** (signing infrastructure likely
  lives in private repo)
- Touches **Subscription** (Play Billing integration tied to
  flavor)

## Authentication

### Confirmed scope

- OAuth required. Bearer-token API keys (v0.1.0 model) insufficient
  for users who aren't the operator.
- **Google OAuth at minimum.**
- Possibly additional OAuth providers.

### Operator decisions needed

- **OAuth providers beyond Google?** Apple? GitHub? Microsoft?
  Email-and-password as fallback?
- **Account creation flow.** Sign up at first OAuth login (single
  step), or distinct sign-up step? Email verification required?
- **Account deletion / data export.** GDPR Article 17 (right to
  erasure) and Article 20 (data portability) — how implemented in
  app?
- **Token refresh strategy.** OAuth refresh token handling, expiry,
  revocation.
- **Multi-device sessions.** Can one user have the app on multiple
  devices simultaneously? Session invalidation on password change?
- **Existing v0.1.0 API key path.** Does the operator's own key
  persist as an admin/operator credential? Or is the operator
  expected to also auth via OAuth post-v0.2.0?
- **Backend identity model.** OAuth "sub" claim as user_id, or
  internal user_id with OAuth sub as foreign key?

### Cross-cutting

- Touches **Subscription** (subscription is per-user; user identity
  must exist before subscription can attach)
- Touches **Backend data isolation** (every backend write needs
  user_id scope)
- Touches **Privacy/legal** (auth provider's data sharing
  practices)

## Subscription & Payment

### Confirmed scope

- Paid app. Not free.
- Subscription model (not one-time purchase).
- Payment infrastructure.

### Operator decisions needed

- **Pricing structure.** Single tier? Freemium with paid features?
  Multiple paid tiers (good/better/best)?
- **Pricing levels.** Actual prices per tier and currency.
- **Payment provider.** Google Play Billing (Android-native, takes
  Google's cut)? Stripe (web/billing portal, your terms)?
  RevenueCat (cross-platform abstraction, even though iOS is out
  for now)?
- **Free tier or trial period.** Free trial? Limited free usage?
  Hard paywall from first transcription?
- **Quota model.** What does a subscription buy?
  - Minutes per month?
  - Number of transcriptions?
  - Total audio bytes?
  - Unlimited with fair-use?
- **Cost-coupling.** Each transcription = real OpenAI API spend.
  Subscription pricing needs to cover marginal cost + margin. How
  do quota tiers map to OpenAI cost?
- **Refund policy.** Aligned with Play Store standards or stricter?
- **Family/team plans.** In v0.2.0 or deferred?
- **Cancellation / pause.** Mid-cycle cancel behavior, prorating,
  grandfathering price changes.

### Cross-cutting

- Touches **Auth** (subscription per user)
- Touches **Reliability** (rate-limit per user prevents one user's
  runaway spend)
- Touches **Privacy/legal** (payment provider's data handling,
  PCI scope)
- Touches **Repo architecture** (payment integration likely lives
  in private repo)

## Privacy & Legal

### Confirmed scope

- Privacy policy (published, linkable)
- Terms of Service (published, linkable, accepted at signup)
- User data handling beyond operator-only

### Operator decisions needed

- **Governing jurisdiction.** Hungary (Robbie's residency)? Other?
  Affects which laws apply to the entity.
- **Data retention policy.**
  - Audio file retention duration after transcription
  - Transcript retention duration
  - User account data retention after deletion
- **Data residency.** Servers are babbie (OVH). Matters for EU
  GDPR. Worth disclosing.
- **GDPR compliance approach.** Data export, deletion, consent,
  legitimate-interest documentation.
- **Audio as "sensitive personal data."** Voice data is biometric
  in some jurisdictions; affects consent requirements.
- **Third-party processor disclosure.** OpenAI handles transcription
  audio. Must be disclosed; users must consent. Data Processing
  Agreement with OpenAI?
- **Age restriction.** Under-13 forbidden (COPPA)? Under-16
  forbidden (GDPR child consent)?
- **Cookie/tracking policy.** What analytics, if any?
- **Business entity.** Does operator need to incorporate to limit
  liability? Sole proprietor sufficient?

### Cross-cutting

- Touches every theme — privacy/legal is a horizontal concern.

## Reliability Hardening

### Confirmed scope

- Address known edge cases that were N=1-acceptable but not
  user-acceptable.
- Specific example surfaced: 25MB OpenAI file size limit.

### Operator decisions needed

- **Reliability targets.** Uptime SLA promised to users? Best
  effort?
- **Per-user rate limiting.** What limits, what backoff, what
  user-facing error messaging?
- **Abuse prevention.** What constitutes abuse? Detection
  approach?
- **Backoff/retry policies.** OpenAI errors, network errors,
  internal errors — what retries, what user surfaces?
- **Failure modes for over-25MB files.** Reject? Auto-chunk
  client-side? Auto-chunk server-side? User-prompted re-encode?
- **Crash recovery / durability** (relates to #81 web client
  pattern, possibly applies to mobile too).
- **Concurrent transcription** per user.

### Cross-cutting

- Touches **Subscription** (quota enforcement is rate limiting)
- Touches **Observability** (failures surfaced to users)

## Repo Architecture

### Confirmed scope

- Open-source `oracy` core stays public
- App-store distribution version forks into a **private repo**
- "Adds a layer or three" — non-trivial operationally

### Operator decisions needed

- **Fork timing.** When does the private fork get created?
  - Before v0.2.0 work begins (now)?
  - After v0.2.0 ships?
  - During v0.2.0 work as the split becomes structurally needed?
- **Public/private boundary.** What lives where?
  - **Public (oracy):** backend core, transcription engine, deploy
    docs, operator-facing infrastructure
  - **Private (likely candidates):** OAuth secrets, payment provider
    integration, signing keys, app store metadata, branded UI
    assets
  - **Ambiguous (decide):** authentication code (could be public
    or private), subscription business logic, UI code
- **Sync strategy.** Public-to-private direction:
  - Periodic squash merge?
  - git subtree?
  - Rebuild from source on each public release?
- **Branding split.** Same app name in store vs. GitHub? Or
  brand the app store version differently from the open source
  project?
- **License.** Public repo's current license, intent for
  open-source community contributions.
- **Operator commitment to OSS.** Long-term: stays open source,
  becomes source-available, eventually proprietary?

### Cross-cutting

- Touches every other theme. The split fundamentally shapes
  development, deployment, and operations going forward.

## Cross-cutting concerns

These are not standalone sections; they propagate across themes
and warrant explicit naming so they don't fall through cracks.

### Multi-user data isolation

The v0.1.0 backend has a single api_key concept (per-key, not
per-user). v0.2.0 needs every data path scoped by `user_id`.

- Database schema additions
- Query scoping audits
- Import/export per user
- Storage organization (audio files keyed by user_id)
- Operator-only data (e.g., system metrics) staying outside
  user scope

### User-facing documentation

Distinct from operator docs. In-app help, FAQ, support contact,
troubleshooting common issues.

**[OPERATOR DECISION NEEDED]** What channels? In-app help screens?
External knowledge base? Support email?

### Cost model integrity

Each user transcription = real OpenAI API spend. Subscription
pricing must cover marginal cost. Edge case: a user paying $X/month
who transcribes more than $X of audio is operator-margin-negative.
Quota structure must prevent this.

## Open questions to resolve before v0.2.0 kickoff

most subsequent work:

   Affects subscription architecture and Play Store integration.

   Without this, scope drifts.

   Affects timeline and budget.
